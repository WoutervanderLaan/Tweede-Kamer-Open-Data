# 1.1 — Reading a table honestly

Module 1.1. Goal: stop trusting what a query *looks like* it returns. By the
end you can say, before running it, how many rows a simple query gives back
and exactly which rows NULL silently removed. ~2.5 hours; each section is a
clean stopping point (A ≈ 30 min, B ≈ 40 min, C ≈ 60 min, D ≈ 30 min).

**How this file works**

Each section opens with a **primer**: read it first. It gives you the mental
model, the vocabulary, and a worked example on a *made-up* library database
(`books`, `loans`) — never the gym tables, so the exercises are still yours
to solve. Each section also says what it **builds toward**, so you know where
the questions are heading.

Questions are labelled:

- 🔮 **Guess** — asked *before* you've been taught the answer, on purpose.
  Being wrong first makes the explanation stick. No wrong answers, not graded,
  never goes into `REVIEW.md`. The explanation follows (in the "Afterwards"
  note or from the tutor).
- ✅ **Check** — the primer taught what you need. Apply it. These are what
  the gate looks like.

Answers in your own words are fine everywhere. What counts is the mechanism,
not the phrasing.

**Where your work goes**

- `queries/1.1-reading-a-table-honestly.sql` — every query you run, numbered
  to match this file. Above each: `-- predict: <number/shape> because <reason>`.
  Below each: `-- actual: <result>`. Wrong predictions stay in.

## A. Get your bearings in `psql`

**Builds toward:** being able to open an unfamiliar database and, in two
minutes, know its tables, their columns, and which columns can be empty.

### Primer A — tables and `psql`

**A table is a set of rows.** Every row has the same columns; every column
has a *type* (`bigint`, `text`, `date`, …) and is either `NOT NULL` (a value
is required) or nullable (the value may be missing — `NULL`). "Set" is the
important word: rows have no position and no built-in order. Section B comes
back to this.

**`psql` has two languages.** Anything starting with a backslash is a
*meta-command*: `psql` itself (the client) handles it, usually by running
catalogue queries for you. It needs no `;`. Everything else is SQL, sent to
the server, and needs a `;` to run.

| Command      | What it does                                                     |
| ------------ | ---------------------------------------------------------------- |
| `\dt`        | list tables                                                      |
| `\dt+`       | same, plus extra details per table                               |
| `\d books`   | columns, types, nullability, defaults, indexes, foreign keys     |
| `\timing`    | toggle: print how long each query took                           |
| `\x auto`    | switch to vertical display when rows are too wide for the screen |
| `\?` / `\h`  | help for meta-commands / help for an SQL command (`\h SELECT`)   |
| `\q`         | quit                                                             |

**Reading `\d` output.** For an imaginary `books` table:

```
   Column       |  Type   | Nullable | Default
----------------+---------+----------+------------------------------
 id             | bigint  | not null | generated always as identity
 title          | text    | not null |
 isbn           | text    |          |
 published_year | integer |          |
```

An empty `Nullable` cell means *NULL is allowed*. So `isbn` and
`published_year` can be missing, but `title` can't. The schema tells you a
value *may* be missing. It doesn't tell you *why* — whether that's "we never
recorded it", "doesn't apply", or something else. Keep that gap in mind.

## B. SELECT without lying to yourself

**Builds toward:** knowing which parts of a SELECT's result are promised and
which are accidents — order, ties, and where NULLs end up.

### Primer B — how a SELECT actually runs

**Written order ≠ run order.** You *write* `SELECT … FROM … WHERE … ORDER BY
… LIMIT`, but Postgres *evaluates* the clauses in this logical order:

```
FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT
```

Each step only sees what the steps before it produced. (`GROUP BY` and
`HAVING` come in 1.3; they're listed so you know where they fit.)

**No `ORDER BY` means no order.** A table is a set, so without `ORDER BY`
Postgres returns rows in whatever order is cheapest to produce. On a freshly
loaded table that's often the insert order, which is why it *looks* stable.
Nothing promises it. `LIMIT 5` without `ORDER BY` means "any five rows".

**`ORDER BY` details that bite:**

- `ASC` (the default) or `DESC`, per column.
- **Ties:** if two rows have the same sort value, their order *between each
  other* is not guaranteed either. Add a second sort column (often `id`) as a
  tie-breaker when it matters — especially with `LIMIT`, where a tie decides
  who makes the cut.
- **NULLs sort as if larger than every value.** So with `ASC` they come
  **last**, and with `DESC` they come **first**. Override with `NULLS FIRST` /
  `NULLS LAST`.

**Expressions and aliases.** A SELECT list can compute things, and `AS` names
the result column:

```sql
-- the three cheapest books, price shown in euros
SELECT title,
       price_cents / 100.0 AS price_eur
FROM books
ORDER BY price_cents, id      -- id breaks ties between equal prices
LIMIT 3;
```

**Integer division truncates.** `7 / 2` is `3` in Postgres, because both
sides are integers. `7 / 2.0` is `3.5`. Use `round(...)` if you want rounding
rather than truncation.

## C. NULL, and logic with three values

**Builds toward:** looking at a `WHERE`, `NOT IN` or `count` and saying
exactly which rows NULL makes disappear — the core skill the 1.1 gate checks.

### Primer C — NULL and three-valued logic

**NULL means "no value here".** It is not `0` and not the empty string `''`.
What it *means* depends on the column, and the database doesn't know which:

- *unknown* — the value exists in reality, we just don't have it (a book's
  publication year nobody recorded);
- *not applicable* — there's nothing to know (a middle name for someone who
  has none);
- *a deliberate signal* — the designers gave NULL a specific meaning (a loan
  with no `returned_on` is still out).

**Comparisons with NULL are neither true nor false — they're UNKNOWN.**
`NULL = 5`, `NULL <> 5` and even `NULL = NULL` all evaluate to NULL (read:
"unknown"). Arithmetic with NULL gives NULL too: `NULL + 1` is NULL. So SQL
has three truth values: TRUE, FALSE, UNKNOWN.

**`WHERE` keeps a row only if the condition is TRUE.** FALSE and UNKNOWN are
both thrown away. So a book with a NULL `published_year` is missing from
*both* of these:

```sql
SELECT count(*) FROM books WHERE published_year = 2001;
SELECT count(*) FROM books WHERE published_year <> 2001;
```

**AND / OR / NOT with UNKNOWN** — the rule is "if the unknown value could
change the outcome, the outcome is unknown":

| Expression          | Result  | Why                               |
| ------------------- | ------- | --------------------------------- |
| `TRUE  AND UNKNOWN` | UNKNOWN | depends on the unknown part       |
| `FALSE AND UNKNOWN` | FALSE   | false no matter what              |
| `TRUE  OR  UNKNOWN` | TRUE    | true no matter what               |
| `FALSE OR  UNKNOWN` | UNKNOWN | depends on the unknown part       |
| `NOT UNKNOWN`       | UNKNOWN | the opposite of unknown is unknown |

**Testing for NULL** needs its own operators, because `=` can't do it:
`x IS NULL`, `x IS NOT NULL`. There are also NULL-safe comparisons:
`x IS DISTINCT FROM y` behaves like `<>` but treats two NULLs as equal and
never returns UNKNOWN (`IS NOT DISTINCT FROM` is the NULL-safe `=`).

**`IN` is shorthand for a chain of `OR`s.** `x IN (a, b)` means
`x = a OR x = b`. Worked example, `published_year IN (2001, NULL)`:

- book from 2001: `TRUE OR UNKNOWN` → TRUE → kept
- book from 1999: `FALSE OR UNKNOWN` → UNKNOWN → dropped

`NOT IN` is the negation of `IN`. Question 12 asks you to work out what that
expands to. Negating an `OR` chain has a standard rule (De Morgan): `NOT (p OR
q)` is `(NOT p) AND (NOT q)`.

**Counting.** Aggregates skip NULLs:

| Expression             | Counts                                        |
| ---------------------- | --------------------------------------------- |
| `count(*)`             | rows                                          |
| `count(isbn)`          | rows where `isbn` is not NULL                 |
| `count(DISTINCT isbn)` | different non-NULL `isbn` values              |

**The meaning decides the query.** For "which loans are still out?" the NULL
*is* the answer: `WHERE returned_on IS NULL`. For "books published before
2000", a NULL year means *we don't know*, so those books belong to neither
"before" nor "after". A report that splits them into two buckets should say
how many it couldn't place.

## D. `DISTINCT` is usually a confession

**Builds toward:** recognising when `DISTINCT` answers a real question and
when it covers up the fact that you don't know what identifies a row.

### Primer D — what DISTINCT really does

**`DISTINCT` removes duplicate *output* rows.** In the run order it comes
after `SELECT`: Postgres first computes the columns you asked for, then drops
rows that are identical across *all* of those columns. (For this purpose two
NULLs count as the same — unlike `=`.) It isn't free: Postgres has to sort or
hash the whole result to find duplicates.

**Honest use:** the question really is about values. "Which countries do our
books come from?" → `SELECT DISTINCT country_code FROM books`. You want each
value once, and that's the answer.

**Confession use:** you got duplicate rows you didn't expect, and `DISTINCT`
makes them go away. Duplicates almost always mean one of two things:

1. a join multiplied rows (Module 1.2 — the most common cause), or
2. the columns you selected don't *identify* the thing you meant. Two
   different books can both be called *Collected Poems*. Select only `title`,
   add `DISTINCT`, and one of them has silently vanished.

Either way `DISTINCT` hides the symptom and leaves the cause. **Identity comes
from a key** — the primary key, or a column with a `UNIQUE` constraint — not
from a descriptive column that happens to *usually* be unique.

**A SELECT doesn't need a table.** `SELECT 7 / 2, 7 / 2.0, NULL = NULL;` just
evaluates expressions. It's the quickest way to test how Postgres treats a
value without touching any data.

## The gate — what it checks

Six queries you haven't seen, all on gym tables, all using only primers A–D
(✅ material — no surprises). For each, before running, you give:

1. **The row count** — as a number, *or* in terms of counts you already know
   (e.g. "all artists minus the ones with a NULL `country_code`"). Either
   counts, if it's right.
2. **What NULL does to it** — which rows (if any) disappear because of NULL,
   and why, in your own words.

**Pass:** at least 5 of 6 correct on both parts. For each miss, you explain
afterwards what actually happened and why. The explanation passes if it names
the mechanism (e.g. "`<>` against a NULL is UNKNOWN, and `WHERE` drops
UNKNOWN"). Exact wording doesn't matter.
