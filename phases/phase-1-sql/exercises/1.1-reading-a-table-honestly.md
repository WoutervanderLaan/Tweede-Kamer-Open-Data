# 1.1 — Reading a table honestly

Module 1.1. Goal: stop trusting what a query *looks like* it returns. By the
end you can say, before running it, how many rows a simple query gives back
and exactly which rows NULL silently removed. ~2 hours; each section is a
clean stopping point (A+B ≈ 50 min, C ≈ 45 min, D ≈ 25 min).

**Where your work goes**

- `queries/1.1-reading-a-table-honestly.sql` — every query you run, numbered
  to match this file. Above each: `-- predict: <number/shape> because <reason>`.
  Below each: `-- actual: <result>`. Wrong predictions stay in.
- `notes/psql-crib.md` — your crib sheet. Grows for the whole phase.
- `notes/1.1-reading-a-table-honestly.md` — written answers, where asked.

The Module 1.1 **gate** is not in this file: six queries you haven't seen,
predicted cold.

---

## A. Get your bearings in `psql`

```sh
make psql
```

1. Run `\dt`. Before running anything else, write down which table you
   think is largest and which is smallest, and a rough row count for each.
   Then run `\dt+`. What does it show you, and what does it *not* show you
   that you wanted?
2. Run `\d artists`. For every column, note whether it can be NULL. For each
   nullable column, write one sentence: *if this is NULL, what does that mean
   in the real world?* Keep these — section C comes back to them.
3. Run `\d subscriptions`. The schema file (`db/init/002_gym_schema.sql`)
   has a comment explaining what a NULL `ended_on` means. Can you see that
   meaning anywhere in `psql`? Where does knowledge like that live on a real
   team, and what happens when it lives nowhere?
4. Turn on `\timing` and `\x auto`. Start `notes/psql-crib.md`: one line per
   meta-command used so far — what it shows, in your own words. Add `\?` and
   `\h SELECT` after trying them.

## B. SELECT without lying to yourself

5. Predict, then run **three times**:

   ```sql
   SELECT id, name FROM artists LIMIT 5;
   ```

   Same rows every time? Write down whether you think that is *guaranteed*,
   and why. (Bring this one to the session either way.)
6. Write a query: the 10 most recently formed artists — name and formed year
   only. **Before running**, predict what the first row will look like.
7. If 6 didn't answer the question you meant to ask, fix it. In notes: does
   your fix *remove* rows or *reorder* them? Name a situation where that
   difference changes the answer someone gets.
8. Write a query listing the 10 longest tracks: title, and duration in whole
   seconds under a column name of your choosing (`AS`). Then predict: can
   you use that new column name in a `WHERE` clause of the same query? In
   `ORDER BY`? Try both. Write down what the results imply about the *order*
   in which Postgres handles the parts of a SELECT.

## C. NULL, and logic with three values

The tutor explains three-valued logic at the start of this section. Working
solo? Read the Postgres docs, *9.2 Comparison Functions and Operators*
(the `IS NULL` / `IS DISTINCT FROM` part), then continue.

9. Write **all three** predictions before running any of them:

   ```sql
   SELECT count(*) FROM artists WHERE country_code = 'NL';
   SELECT count(*) FROM artists WHERE country_code <> 'NL';
   SELECT count(*) FROM artists;
   ```

   Does (first + second) equal the third? If not, where did the difference
   go? Account for every missing row with a query of your own.
10. Predict, then run:

    ```sql
    SELECT count(*) FROM artists WHERE country_code = NULL;
    ```

    Why doesn't Postgres raise an error for this?
11. Without running anything, rank these from largest to smallest (ties
    allowed), then write a single query that returns all three side by side:
    `count(*)`, `count(country_code)`, `count(DISTINCT country_code)` on
    `artists`.
12. Write both predictions first:

    ```sql
    SELECT count(*) FROM artists WHERE formed_year NOT IN (1990, 1991);
    SELECT count(*) FROM artists WHERE formed_year NOT IN (1990, NULL);
    ```

    Explain the second result step by step: rewrite `NOT IN (1990, NULL)` as
    the `AND`/`<>` expression it really is, and evaluate it by hand for an
    artist formed in 1975. In notes: where would a NULL sneak into a `NOT IN`
    list in real code without anyone typing `NULL`?
13. Two tables, two NULLs, two different meanings:
    - Write a query: how many subscriptions are **currently running**?
    - Write a query: how many albums have an **unknown** release date?

    Then predict and run your own pair: albums released before 2000, and
    albums released in or after 2000. In notes: the rows missing from that
    pair — are they old albums, new albums, or neither? Contrast with
    `subscriptions.ended_on`: what is different about what NULL *means*
    there, and does that change how a query should treat it?

## D. `DISTINCT` is usually a confession

14. Predict whether these two numbers match, then run:

    ```sql
    SELECT count(*) FROM artists;
    SELECT count(DISTINCT name) FROM artists;
    ```

    Then predict how many rows this returns, and run it:

    ```sql
    SELECT * FROM artists WHERE name = 'The Velvet Foxes';
    ```

    In notes: a search endpoint runs `SELECT DISTINCT name FROM artists WHERE
    ...` to "clean up duplicates". What has it just done to a user looking
    for the second band? What should identity rest on instead?
15. `users.email` is `UNIQUE`. Without touching any table, write a one-line
    `SELECT` that proves whether Postgres considers `User7@example.com` and
    `user7@example.com` the same value. Then, in notes: what does this mean
    for a login form, and for that `UNIQUE` constraint? (Don't fix the data —
    the mixed case is planted.)
16. One sentence each, in notes: when is `DISTINCT` the honest answer to a
    question, and when is it hiding something? Use 14 as one of your two
    examples.
